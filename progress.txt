Design choice — `package-info.java` over `.gitkeep`:
- `.gitkeep` would persist the directory in Git but javac would never see those packages — they'd have no compiled `Package` object, no place to attach package-level annotations, and tools like Spring's component scan or static analyzers would skip them. `package-info.java` is the idiomatic Java answer: it's a real source file that javac recognizes, anchors the package in the compiled module, and gives us a per-package documentation slot for free. Cost is 37 single-line files; benefit is that every leaf package is a first-class Java entity from day one.

Design choice — empty `@Configuration` classes for `config/`:
- Architecture.md §3 names exactly three classes (`WebConfig`, `JacksonConfig`, `OpenApiConfig`). I created them as empty `@Configuration`-annotated classes rather than as bare placeholder files because: (1) the annotation makes Spring aware of them at component-scan time, so future tasks can add `@Bean`/`@EnableWebMvc`/etc. methods without changing the class declaration; (2) an empty `@Configuration` registers no beans and has no runtime cost; (3) it documents intent — someone reading these classes knows immediately they're meant to host beans.

Follow-up risk / notes:
- `OpenApiConfig` is a forward-looking placeholder. There's no springdoc or OpenAPI dependency in `pom.xml` (TASK-007 didn't include it). If we never add OpenAPI, this class can be deleted without consequence. Leaving it because architecture.md §3 lists it explicitly.
- `JacksonConfig` is also forward-looking — Spring Boot's default Jackson config is fine for the MVP. Keep the class in place so when we eventually need `JavaTimeModule` tweaks or custom serializers (likely once Gantt date payloads start round-tripping `LocalDate`/`Instant`), we have a home for them without inventing a new file.
- `package-info.java` files use one-liner javadocs with implementation hints (e.g. "CORS wiring lands here in TASK-010", "Source of truth for task mutations (architecture.md §12)"). These are anchors for future agents working through the task list — when TASK-010 starts, grep for "TASK-010" in package-info files surfaces `WebConfig`'s comment immediately. If those task-id breadcrumbs feel noisy later, they're cheap to remove in TASK-081's polish pass.
- Empty `@Configuration` classes mean Spring's component scan now sees three more configurations than before. No `@Bean` methods are registered, so no measurable startup-time difference and no functional change. Design choices and trade-offs:
- `CorsConfigurationSource` bean vs `WebMvcConfigurer.addCorsMappings(...)`: chose the bean. Spring Security 6 (which is on the classpath now and gets a real `SecurityFilterChain` in TASK-024) consumes a `CorsConfigurationSource` bean automatically when `.cors(Customizer.withDefaults())` is called on `HttpSecurity`. The `addCorsMappings` MVC hook only runs *after* the security filter, so a preflight `OPTIONS` would already be 401'd by Spring Security before MVC sees it. The bean approach is the canonical "CORS-with-Spring-Security" pattern and avoids a refactor in TASK-024.
- `HealthController` lives at `com.trackify.common.HealthController` rather than under a new `common/health/` subpackage. Architecture.md §3 lists `common/{exception,response,security,util}` only; no `health` package was specified. A single top-level file in `common/` is cheaper than inventing a new subpackage for one class. If the controller grows (readiness, build info, etc.), promote to `common/health/` then.
- `Map<String, String>` return type instead of a dedicated `HealthResponse` record. The payload is one key, never sent over a typed client, and the architecture makes no claim about a stable health-payload schema. A record would be 5 extra lines for zero added safety — TASK-011 (global error shape) is where typed response envelopes earn their keep.
- `excludeAutoConfiguration = SecurityAutoConfiguration.class` in the test slice instead of `@AutoConfigureMockMvc(addFilters = false)`. Both would pass today, but excluding the autoconfig is cleaner: it removes Spring Security from the slice entirely so the test never touches `UserDetailsService`, `PasswordEncoder`, or `SecurityFilterChain` autoconfig — none of which are correctly wired until TASK-024. `addFilters = false` would still spin up the security beans and just bypass the filter at request time, which is more fragile to future autoconfig changes.
- `@TestPropertySource` over a `@Bean CorsConfigurationSource` mock. The `WebConfig` is real Spring config under test (its `@Value` placeholders must resolve), and stubbing it would mean the test no longer covers the config wiring. Providing the four properties is 4 lines and exercises the real bean.

Follow-up risk / notes:
- The CORS bean only takes effect once the security filter chain calls `.cors(...)`. Until TASK-024 lands, **no actual CORS handling happens at runtime** — Spring Security's default chain returns 401 for preflight `OPTIONS` requests before the bean is consulted. This is intentional: TASK-010 lays the bean, TASK-024 wires it. The MockMvc test does NOT cover preflight behavior because preflights are filter-chain concerns; trust TASK-024 to add a CORS-aware test (or extend `HealthControllerTest` then).
- `WebConfig` no longer implements `WebMvcConfigurer`. If a future task wants per-controller CORS overrides via the MVC registry, it'll need to add the interface back and override `addCorsMappings`. Recommend keeping CORS centralized in the bean.
- `@Value("${trackify.cors.allowed-origin}")` will fail context startup if `FRONTEND_ORIGIN` isn't set AND the active profile isn't `local` (because `application.yml` resolves it to `${FRONTEND_ORIGIN}` with no default, while `application-local.yml` defaults it to `http://localhost:5173`). That's the intended fail-fast behavior for prod-shaped boots — operators must set `FRONTEND_ORIGIN` explicitly. Mentioned in TASK-008 progress already; restating because TASK-010 now actually depends on it being set.
- `allowedHeaders` is bound as `String[]` even though `application.yml` currently has the single value `"*"`. Future-proofing for cases like `Authorization,Content-Type,X-Requested-With` without revisiting WebConfig. `Arrays.asList(allowedHeaders)` always returns a non-empty list.
- `allowCredentials=true` + a specific origin (`http://localhost:5173` in local) is CORS-spec compliant. If anyone ever sets `allowed-origin: "*"`, the browser will reject responses because credentialed wildcards aren't allowed. Worth a one-liner in TASK-081's runbook.
- `HealthController` has no `@PreAuthorize` or other security annotations — it relies on TASK-024's `permitAll()` for `/api/health`. The class javadoc points at TASK-024 as the contract owner.
- `excludeAutoConfiguration = SecurityAutoConfiguration.class` in the slice test is slightly load-bearing: when TASK-024 adds an explicit `@Configuration class SecurityConfig` with its own `SecurityFilterChain` bean, the slice will still load it (slices include `@Configuration` classes by default). At that point, either: (a) the SecurityConfig will permit `/api/health` and the test still passes, or (b) we'll need to switch to `@WithMockUser` or add `excludeFilters` to the slice. Re-evaluate when TASK-024 lands.
- First test in the project — established the convention `backend/src/test/java/com/trackify/<module>/...Test.java` mirroring the `src/main/java` layout. TASK-011 (error-shape test), TASK-024 (security chain test), TASK-026 (registration unit test), etc. should follow the same path.
- `pom.xml` already has `spring-boot-starter-test` (TASK-006) and `spring-security-test` (TASK-007) at `test` scope; no dep changes needed for this task. Mockito agent warning in test output is a Spring Boot 3.4 + JDK 21 noise message about dynamic agent loading — harmless, will be resolved when Mockito 5.x fixes self-attach. Not a TASK-010 concern.
