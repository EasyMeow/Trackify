Design choice — `package-info.java` over `.gitkeep`:
- `.gitkeep` would persist the directory in Git but javac would never see those packages — they'd have no compiled `Package` object, no place to attach package-level annotations, and tools like Spring's component scan or static analyzers would skip them. `package-info.java` is the idiomatic Java answer: it's a real source file that javac recognizes, anchors the package in the compiled module, and gives us a per-package documentation slot for free. Cost is 37 single-line files; benefit is that every leaf package is a first-class Java entity from day one.

Design choice — empty `@Configuration` classes for `config/`:
- Architecture.md §3 names exactly three classes (`WebConfig`, `JacksonConfig`, `OpenApiConfig`). I created them as empty `@Configuration`-annotated classes rather than as bare placeholder files because: (1) the annotation makes Spring aware of them at component-scan time, so future tasks can add `@Bean`/`@EnableWebMvc`/etc. methods without changing the class declaration; (2) an empty `@Configuration` registers no beans and has no runtime cost; (3) it documents intent — someone reading these classes knows immediately they're meant to host beans.

Follow-up risk / notes:
- `OpenApiConfig` is a forward-looking placeholder. There's no springdoc or OpenAPI dependency in `pom.xml` (TASK-007 didn't include it). If we never add OpenAPI, this class can be deleted without consequence. Leaving it because architecture.md §3 lists it explicitly.
- `JacksonConfig` is also forward-looking — Spring Boot's default Jackson config is fine for the MVP. Keep the class in place so when we eventually need `JavaTimeModule` tweaks or custom serializers (likely once Gantt date payloads start round-tripping `LocalDate`/`Instant`), we have a home for them without inventing a new file.
- `package-info.java` files use one-liner javadocs with implementation hints (e.g. "CORS wiring lands here in TASK-010", "Source of truth for task mutations (architecture.md §12)"). These are anchors for future agents working through the task list — when TASK-010 starts, grep for "TASK-010" in package-info files surfaces `WebConfig`'s comment immediately. If those task-id breadcrumbs feel noisy later, they're cheap to remove in TASK-081's polish pass.
- Empty `@Configuration` classes mean Spring's component scan now sees three more configurations than before. No `@Bean` methods are registered, so no measurable startup-time difference and no functional change. ## 2026-04-26 — TASK-011: global API error shape

- `backend/src/main/java/com/trackify/common/response/ApiError.java` (new): immutable record envelope returned by every error path. Fields: `status` (int), `error` (String code: `NOT_FOUND` / `VALIDATION_FAILED` / `INTERNAL_ERROR`), `message`, `path`, `timestamp` (`Instant`), `details` (nullable `List<FieldViolation>`). Design choices and trade-offs:
- **Record over class for `ApiError`** — Java 17+ records make the envelope immutable, give us a sane `equals`/`hashCode`/`toString` for free, and eliminate the boilerplate that would otherwise tempt us to add Lombok. Jackson serializes records via their canonical accessors with no extra config.
- **`@JsonInclude(NON_NULL)` on the record itself, not per field** — only `details` is conditional today, but applying the annotation at the record level future-proofs for additional optional fields without touching the annotation each time. Cost: zero. The `notFoundExceptionReturnsApiErrorEnvelope` test asserts `$.details` is `doesNotExist()` (not `isNull()`) so this behavior is locked down by a regression test.
- **Three handlers, not five** — task spec says "validation, not found, and generic server errors". Resisted the urge to also handle `ConstraintViolationException` (path/query-param validation), `HttpMessageNotReadableException` (malformed JSON), `MissingServletRequestParameterException`, etc. Those are correctly TASK-077's scope ("standardize 401/403/404"). The `Exception` catch-all handles them today by returning 500, which is wrong for malformed-JSON (should be 400) but acceptable until TASK-077 adds explicit handlers.
- **`error` field as a string code, not an enum** — codes like `"NOT_FOUND"` are stable contract for the frontend. Modeling them as a Java enum would be tidier internally but force consumers to track every code we add; a string keeps the contract open and matches what HTTP status semantics already convey. The `status` field carries the HTTP status separately so clients can match on either.
- **`message` for `INTERNAL_ERROR` is the literal string `"Unexpected server error"`** — never the original exception's message. This avoids leaking stack-trace fragments, SQL fragments, or internal class names to clients. The real cause is logged via SLF4J at ERROR level so operators can debug. If a 5xx ever needs a client-facing hint, add a separate `"correlationId"` field rather than leaking `ex.getMessage()`.
- **Test-only `TestController` as a static inner class** — keeps the test self-contained (no `@Profile("test")` controllers leaking into prod scans). The `@Import` is required because `@WebMvcTest(controllers = TestController.class)` only registers controllers that are *also* in the test slice's component scan; static inner classes outside `@Configuration` aren't auto-scanned, hence the explicit import. `GlobalExceptionHandler` is also explicitly imported because slices don't pick up `@RestControllerAdvice` beans by default.
- **`HttpServletRequest` injection vs `WebRequest`** — both are equivalent for our `getRequestURI()` use case. Picked `HttpServletRequest` because the `jakarta.servlet` API is already on the classpath via `spring-boot-starter-web` and it's the lower-friction choice. If we ever go reactive (we won't for this MVP), this would need to switch to `ServerWebExchange`.

Follow-up risk / notes:
- The `Exception.class` catch-all sits next to the more-specific `NotFoundException` and `MethodArgumentNotValidException` handlers. Spring MVC routes to the most-specific match, so the catch-all only fires for genuinely unhandled types — but if a future handler is added without considering ordering (e.g. `@ExceptionHandler(RuntimeException.class)`), it would silently shadow more-specific handlers. When TASK-077 adds new types, prefer narrowing via concrete classes (`AccessDeniedException`, `AuthenticationException`) rather than broadening up the hierarchy.
- The catch-all logs `ex.getMessage()` only at `ERROR` along with the full stack trace. There's no correlation ID yet — operators have to grep timestamps. Acceptable for a self-hosted MVP; revisit when/if observability is added (out of MVP scope per the architecture doc).
- `MethodArgumentNotValidException` only fires for `@Valid @RequestBody` failures. Validation on `@RequestParam`/`@PathVariable` (which throws `ConstraintViolationException`) is currently uncovered — those will fall to the catch-all and return 500 instead of 400. No DTOs use those validators yet (TASK-026, TASK-041, TASK-050, TASK-055 are the first), so the gap is invisible today. TASK-077 should add the missing handler.
- `details` is omitted (not `[]`) when there are no field violations. Frontend parsers must tolerate the field's absence — TASK-079 (toast notifications for failed mutations) needs to handle both `details === undefined` and `details === []`. Worth noting in that task's progress entry when it lands.
- `@JsonInclude(NON_NULL)` won't strip empty collections — only `null`. `MethodArgumentNotValidException` always produces at least one field error (Spring wouldn't have thrown otherwise), so `details` is never an empty list in practice, but if a future handler creates an `ApiError` with `details = List.of()`, it'll serialize as `"details": []`. Consider switching to `JsonInclude.Include.NON_EMPTY` if that becomes an issue.
- `server.error.include-message: always` and `include-binding-errors: always` in `application.yml` (TASK-008) only affect Spring's *default* error attributes. With `GlobalExceptionHandler` registered, those defaults are bypassed for any exception we handle — so flipping them won't change `ApiError` output. They still apply to Tomcat-level errors that never reach Spring (e.g. 404 for unmapped routes). For full consistency we'd need a custom `ErrorController`, but that's TASK-077 territory.
- `pom.xml` unchanged. No new dependencies. Spring Boot's bundled `jackson-databind` already supports record serialization (since Jackson 2.12).
- **Slice test caveat for TASK-024**: `@WebMvcTest` excludes `SecurityAutoConfiguration`. When TASK-024 adds an explicit `@Configuration class SecurityConfig`, the slice will discover it via component scan and the test will need either `@WithMockUser` or `excludeFilters = @ComponentScan.Filter(type = ASSIGNABLE_TYPE, classes = SecurityConfig.class)`. `--legacy-peer-deps` decision (the React 19 vs gantt-task-react peer-dep conflict TASK-013 flagged):
- First attempt without the flag failed with `ERESOLVE`: `gantt-task-react@0.3.9` declares `peer react@"^18.0.0"`, but the scaffold installed React 19.2.5 (TASK-013). Future `npm ci` invocations don't need the flag to reproduce the install (verified mentally — `npm ci` consumes the lockfile directly and skips peer-dep validation by design).

- **Imports inside the provider, not exported from a separate `themeStyles.ts` barrel**: pulling CSS into the provider's own module file means consumers can't accidentally render `<ThemeProvider>` without the styles also loading — the two are coupled by the import graph, not by convention. When dark mode actually lands (post-MVP), the provider grows a `useState`/`useEffect` pair and exposes a context.
- **Set `data-theme` instead of importing different CSS files for light/dark**: the token file is a single source of truth. Adding an alias just for two import lines is scope creep; if the codebase grows enough that relative paths get painful, a future polish task can add `@/` and codemod imports. Design choices and trade-offs:
- **`useState(() => new QueryClient(...))` instead of a module-level `const client = new QueryClient(...)`**: both work for an SPA with no SSR, but the `useState` lazy-init pattern (a) survives StrictMode's double-mount in dev without recreating the client (the lazy initializer only runs once because `useState` ignores subsequent calls on the same hook), (b) localizes the client to the provider rather than a module-level singleton that's harder to reset for tests, and (c) is the pattern the official TanStack Query React docs recommend for Vite/CRA apps. Cost: zero. Benefit: no foot-guns later.
- **`staleTime: 30_000` (30 seconds)**: TanStack Query's default `staleTime: 0` would refetch every time a hook re-mounts (e.g., navigating between board and timeline pages and back) — wasteful when the underlying data didn't change. 30s is a conservative middle ground: long enough that route navigation in a single flow (dashboard → project → drawer → back) doesn't trigger refetches, short enough that returning after a coffee break gets fresh data. Per-query overrides will tune this for `/api/me` (longer; auth state) and for the board endpoint (shorter once the move/create mutations land in TASK-058+ and want fresher reads). 30s is the safe default.
- **`refetchOnWindowFocus: false`**: TanStack Query's default `true` is great for dashboards but creates a subtle UX wart for an SPA — switching to a Slack tab and back triggers a refetch storm across every mounted query. For a project-management tool where users tab-switch constantly, the surprise loading flicker isn't worth the freshness gain. Mutations and explicit `invalidateQueries` calls handle freshness deterministically. If a future task wants live-feeling staleness on the board or timeline, it can override per-query.
- **`retry: 1` on queries, `retry: 0` on mutations**: queries get one retry to ride through a transient network blip without surfacing an error to the user; more retries would mask real outages with long loading spinners. Mutations get zero retries because retry-on-mutation can double-submit (create the same task twice if the first request actually succeeded but the response was lost). Idempotency via PATCH/PUT minimizes this risk for some endpoints, but POST `/api/projects/.../tasks` and POST `/api/tasks/.../comments` are non-idempotent — retrying them is dangerous. Better to let the mutation fail loudly and let the user click again or let TASK-079's toast surface it.
- **No `QueryClientProvider` re-export from `QueryProvider`**: keeping the boundary clean. Consumers import `QueryProvider` (composition root) and `useQuery`/`useMutation` directly from `@tanstack/react-query` (call sites). Re-exporting hooks would just create a maintenance burden.
- **No Devtools wired up**: `@tanstack/react-query-devtools` isn't in `package.json`. Adding it is a polish task for later (TASK-080-ish range). For now, the build stays minimal and the production bundle stays unencumbered.
- **Provider nesting `<QueryProvider><ThemeProvider><App /></ThemeProvider></QueryProvider>`**: server state is the outermost concern that the entire app — including any future error boundaries, auth flow, and theming — depends on. ThemeProvider is purely visual and has no dependency on Query. If they were swapped, ThemeProvider could still work, but the convention in the TanStack ecosystem is to keep `QueryClientProvider` at or near the top so dev tools and future Suspense boundaries see the full tree. TASK-030 will wrap `AuthProvider` *inside* QueryProvider (so `useQuery` for `/api/me` works) and either inside or outside ThemeProvider (likely inside, so the auth UI inherits theme tokens; final shape TBD by TASK-030).
- **No `ErrorBoundary` or `Suspense` wrapper here**: TanStack Query 5 supports Suspense via `useSuspenseQuery`, but rolling out a top-level `<Suspense>` requires page-level designs for fallbacks, and the architecture defers this to per-screen loading/empty/error states (TASK-078). Not now.

Design choices and trade-offs:
- **UUID primary key with `gen_random_uuid()` instead of `BIGSERIAL`**: V1's whole purpose is to enable the `pgcrypto` extension — that's a strong hint that domain entities are meant to use UUIDs. UUIDs avoid the "guessable id" enumeration vector for an authentication identity (predictable `BIGSERIAL` ids let an attacker brute-force user existence; UUIDs don't), make test fixtures portable across environments without sequence resets, and let later code mint ids client-side or in JPA before persistence. The downside is 16-byte vs 8-byte storage and slightly slower btree scans — irrelevant for an MVP user table. Architecture.md §10 doesn't constrain the choice; UUID is the reasonable default for the first DDL migration and sets the pattern for `workspaces`, `projects`, `tasks` later.
- **Plain `UNIQUE` on `login` and `email` (case-sensitive) instead of `LOWER(login)` functional unique index or `CITEXT`**: the smallest schema delta that satisfies the acceptance criteria. Case-folding at the DB layer would either need the `citext` extension (not enabled in V1; would require either editing V1 — forbidden — or adding a new V2 prelude) or a `CREATE UNIQUE INDEX ON users (LOWER(login))` (also fine but a separate index on top of the UNIQUE constraint, doubling index space). The cleanest split is: application layer (TASK-026, registration service) normalizes login and email to a canonical lowercase form before insert, and the plain UNIQUE constraint enforces uniqueness over the already-normalized values. This matches how the Spring `auth` module intends to handle credential lookups (see architecture.md §7.2 — login/password validation lives in `auth.application`). If a future task discovers normalization gaps, adding `LOWER(...)` indexes is a backward-compatible V*+1 migration.
- **No length CHECK constraints** (e.g., `login VARCHAR(64)`, `display_name VARCHAR(120)`): the MVP has no UI mockup that pins these limits, and Postgres TEXT has no storage cost difference vs VARCHAR(n) anyway. Length validation belongs to Bean Validation annotations on the DTO (TASK-022 will add `@Size` on the registration request, not on the entity) so the rules can move with UI changes without DB migrations. Avoiding CHECK constraints here also keeps room for future profile fields (longer display names, richer email handles) without a fragile schema rewrite.
- **No nullable `last_login_at` or `is_active` flag**: out of scope. The acceptance criteria literally lists "login, email, password hash, display name, and timestamps" — adding fields not asked for is the kind of scope creep CLAUDE.md warns against ("Don't add features beyond what the task requires"). Disabling/locking accounts and tracking last sign-in time are real concerns but they belong to dedicated future tasks with explicit UX (admin disables a user; reauth on suspicious activity).
- **Separate `created_at` and `updated_at` despite no trigger to maintain `updated_at`**: keeping both columns in the initial DDL avoids a follow-up migration when JPA/JPA's `@LastModifiedDate` lands in TASK-022's entity. The DEFAULT `now()` on `updated_at` covers the row's first write; subsequent writes are JPA's responsibility (Spring Data's `@EnableJpaAuditing` + `@LastModifiedDate` is the typical pattern). No DB trigger is necessary or desirable — keep the side-effects in the application layer where they're testable.
- **Named unique constraints (`users_login_unique`, `users_email_unique`) instead of inline `UNIQUE`**: predictable constraint names make integration tests assert on the violation error (`DataIntegrityViolationException` exposes the constraint name in its `cause.message` chain) without relying on Postgres' auto-generated `users_login_key`/`users_email_key` defaults. TASK-026's acceptance criteria explicitly says "rejects a duplicate login" — being able to assert "the constraint named `users_login_unique` fired" is more robust than parsing free-form error text.

TASK-022 — Add the User entity and repository
Date: 2026-04-26
================================================================================

What changed:
- `backend/src/main/java/com/trackify/user/domain/User.java`: new JPA entity. Maps the `users` table created by V2 migration. Fields: `id` (UUID, @Id @GeneratedValue(strategy=UUID)), `login`/`email`/`passwordHash`/`displayName` (String, NOT NULL), `createdAt`/`updatedAt` (Instant, NOT NULL). Protected no-arg constructor for JPA. Public constructor takes the four user-supplied fields; id is filled by Hibernate, timestamps by entity lifecycle hooks (see below). Getters for all fields; setters only on the four user-mutable fields (no setter on `id`, `createdAt`, or `updatedAt` — those are managed). No equals/hashCode override — default Object identity used (see Design choices).
- **`@PrePersist` / `@PreUpdate` lifecycle hooks** populate `createdAt` and `updatedAt` from `Instant.now()`. **Reviewer-flagged fix**: the initial draft left both timestamp fields null and relied on the DB `DEFAULT now()` to populate them — but Hibernate includes every mapped column in the generated INSERT (even when null), which bypasses the DB default and would have triggered a NOT NULL violation on the first `save()`. Lifecycle hooks set both fields in-memory before insert (and bump `updatedAt` on every update), so JPA always sends non-null values. The DB defaults remain as a safety net for non-JPA inserts (migrations, psql scripts).
- `backend/src/main/java/com/trackify/user/infrastructure/UserRepository.java`: new Spring Data JPA repository extending JpaRepository<User, UUID>. Exposes: `findByLogin(String)`, `findByEmail(String)` (both Optional<User>), `existsByLogin(String)`, `existsByEmail(String)`. These are the exact lookups TASK-026 (registration) and TASK-027 (login) will need; nothing else was added.

What was tested:
- `./mvnw compile`: BUILD SUCCESS, 47 source files compiled (includes new User.java and UserRepository.java), exit 0.
- `./mvnw test`: BUILD SUCCESS, 4/4 tests pass (HealthControllerTest x1, GlobalExceptionHandlerTest x3). No regressions. The ERROR-level stack trace in test output is expected — it is the GlobalExceptionHandler's intentional log for a test that provokes a 500, not a test failure.

Design choices and trade-offs:
- **No equals/hashCode override**: JPA entities with UUID PKs have a classic pitfall — id is null until after the first flush, so any `equals` that uses id will incorrectly treat two new, equal-value instances as unequal pre-persist and then "become equal" post-persist, breaking HashSet semantics. The cleanest solution for an MVP where no `Set<User>` or map-keyed-by-user is in scope is to leave Object identity in place. If set membership ever matters, the safe pattern is `equals` based on non-nullable business key (login or email is unique and non-null from construction) rather than the mutable/nullable id.
- **`Instant` for timestamps** (not `OffsetDateTime` or `LocalDateTime`): `TIMESTAMPTZ` stores an absolute UTC point; `Instant` maps to it most directly via Hibernate 6's JDBC type mapping for `timestamp with time zone`. `OffsetDateTime` works too but carries a zone offset that Postgres normalizes to UTC anyway — `Instant` is simpler and avoids accidental offset-arithmetic bugs.
- **`@GeneratedValue(strategy = GenerationType.UUID)**: Hibernate 6 (shipped with Spring Boot 3.x) has first-class UUID generation — no sequence, no DB function call from the JPA side, no custom `@GenericGenerator`. The V2 migration's `DEFAULT gen_random_uuid()` remains as a DB-side safety net for rows inserted outside JPA (migrations, psql scripts), but Hibernate will typically assign the UUID before the insert statement fires.
- **`updatable = false` on `id` and `createdAt`**: prevents accidental overwrite via `merge`.
- **`@PrePersist`/`@PreUpdate` over `@EnableJpaAuditing` for `updatedAt`**: standard JPA lifecycle hooks live on the entity itself, need no `@Configuration` change, and run regardless of how the entity is saved. Spring Data auditing (`@CreatedDate`/`@LastModifiedDate` + `@EnableJpaAuditing`) is the more idiomatic choice once auditing config is wired more broadly (e.g., `@CreatedBy` to track which user touched a row), but for a single field on one entity the lifecycle-hook approach is simpler, has fewer moving parts, and avoids a Spring config change that's outside TASK-022's scope.
- **Repository in `infrastructure` package, not `domain`**: Spring Data repositories are infrastructure concerns (they generate SQL and talk to a database); domain code should not import them. Controllers and application services (TASK-026/027) will inject `UserRepository` directly until a persistence adapter layer is warranted.

Follow-up risk / notes:
- **`ddl-auto: validate` will fail on app boot if entity diverges from migration**: intentional. The seven `users` columns (id, login, email, password_hash, display_name, created_at, updated_at) map 1-to-1 to the entity fields. Any future schema change must be a new Flyway migration, not an entity-only change.
- **Lifecycle hooks vs Spring auditing**: when later tasks need `@CreatedBy`/`@LastModifiedBy` (audit who-did-what fields), the lifecycle-hook approach used here will be replaced by `@EnableJpaAuditing` + `@CreatedDate`/`@LastModifiedDate`/`@CreatedBy`/`@LastModifiedBy`. Both approaches map to the same DB columns; migrating from one to the other is a non-breaking, in-place change. No risk of stale `updatedAt` in the meantime — the hooks fire on every save.
- **No `UserService`, no registration DTO, no Spring Security wiring**: those are TASK-026 and TASK-027. This task deliberately stops at the persistence layer.
- **`existsByLogin` / `existsByEmail`**: Spring Data derives these as `SELECT count(*) > 0 FROM users WHERE login = ?` — efficient, no entity hydration. Added now because they are the cheapest way for the registration service to reject duplicates before attempting an insert, avoiding a round-trip on constraint violation.
- **Reviewer note**: the lifecycle-hook fix was applied after a code-review pass flagged the original null-timestamp insert bug. Final compile + test run was re-executed after the fix; both succeeded. This is the kind of subtle JPA pitfall worth remembering — `@Column(nullable=false)` plus a NOT NULL DB column plus a DB DEFAULT does **not** automatically defer to the default when the entity field is null. Either set the field in code (constructor, lifecycle hook, or auditing) or set `insertable=false` on the column to force Hibernate to omit it from the INSERT.

Date: 2026-04-26
================================================================================

What changed:
- `backend/src/main/java/com/trackify/config/SecurityConfig.java`: new `@Configuration` class. Defines a single `SecurityFilterChain` bean built from the injected `HttpSecurity` and the existing `CorsConfigurationSource` from `WebConfig` (TASK-010). Authorization rules in declaration order: `/api/health` and `/api/auth/**` permitAll; `/error` permitAll; everything else under `/api/**` authenticated; `anyRequest()` denyAll. Session creation policy: `IF_REQUIRED` (default — explicit so the intent is on the page). Form login, HTTP Basic, and the auto-registered `/logout` endpoint are all disabled (`AbstractHttpConfigurer::disable`) — this is a JSON API consumed by an SPA, not a server-rendered app. CSRF is disabled (see Design choices). Authentication entry point is `HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)` so unauthenticated requests to protected paths return a clean 401 instead of Spring Security's default behavior (which depends on which auth mechanism is registered).
- `backend/src/test/java/com/trackify/config/SecurityFilterChainTest.java`: new test using `@WebMvcTest(controllers = HealthController.class)` + `@Import({SecurityConfig.class, WebConfig.class})`. Two tests: `healthIsPublic()` — GET `/api/health` returns 200 anonymous; `protectedRouteReturnsUnauthorizedWhenAnonymous()` — GET `/api/me` returns 401 anonymous. Notably, `/api/me` is not yet implemented (TASK-028 owns it) but Spring Security's `AuthorizationFilter` runs ahead of the dispatcher servlet and emits 401 before route matching ever happens — so the test exercises the filter chain rule, not a controller method. Same `@TestPropertySource` block as `HealthControllerTest` to satisfy `@Value` injection in `WebConfig`.

What was tested:
- `./mvnw -q compile`: clean (no output = exit 0). 48 source files compiled.
- `./mvnw test`: BUILD SUCCESS. Tests run: 6, Failures: 0, Errors: 0, Skipped: 0. Breakdown: SecurityFilterChainTest x2 (new), HealthControllerTest x1, GlobalExceptionHandlerTest x3. The ERROR-level stack trace in the raw output is the GlobalExceptionHandler's expected log line from the test that intentionally provokes a 500 — not a failure. No regressions in pre-existing tests.

Design choices and trade-offs:
- **CSRF disabled for the API**: the SPA + cookie pattern's CSRF defense in this app is the combination of (a) `SameSite=Lax` on the session cookie (already set in `application.yml`: `SERVER_SERVLET_SESSION_COOKIE_SAME_SITE:lax`), which blocks cross-site form submissions from initiating state-changing POSTs that carry the cookie, and (b) the `CorsConfigurationSource` from `WebConfig` restricting allowed origins to `FRONTEND_ORIGIN` only, blocking credentialed XHR from other origins. Spring Security's default CSRF token mechanism is built for HTML form POSTs and would require either a `CookieCsrfTokenRepository` + an `XSRF-TOKEN` header on every mutation from the SPA's `httpClient`, or a `CsrfTokenRequestAttributeHandler` for SPAs — both add real frontend complexity that is out of scope for the MVP. Architecture.md does not call out CSRF separately. The trade-off: if the SPA is ever served from a different origin under credentialed CORS (allow-credentials true with a wildcard origin) or `SameSite=None`, CSRF would need to be re-enabled before that change ships. Documented here so the next person sees the full picture.
- **`/api/auth/**` permitAll instead of just `/api/auth/login`**: the auth phase will land `/api/auth/login`, `/api/auth/register`, and (future) password-reset endpoints. Permitting the whole `/api/auth/**` prefix avoids touching `SecurityConfig` again for every subsequent auth endpoint while still keeping a clear, narrow public surface (no other prefix is permitAll). The login/register handlers themselves will validate inputs; the security filter chain only decides whether the request is allowed past the gate. `/api/logout` (TASK-029) is intentionally not under `/api/auth/**` — it requires an authenticated session to invalidate, so it falls under the default authenticated rule.
- **`/error` permitAll**: Spring Boot dispatches uncaught exceptions to the `/error` servlet path. If Security blocks `/error`, an unauthenticated request that triggers an exception in a permitted path could 401-loop on its own error page. Permitting `/error` lets the `GlobalExceptionHandler` (TASK-011) render the proper `ApiError` envelope. There is no information disclosure risk: the `GlobalExceptionHandler` controls the response body explicitly and never echoes server internals.
- **`anyRequest().denyAll()`**: explicit denial outside `/api/**` is safer than `permitAll` — Spring Boot does not serve any non-API content from this app (the SPA is a separate Vite-built static bundle on `FRONTEND_ORIGIN`), so denying everything else closes the door on accidental endpoint exposure (e.g., a future Spring Boot starter that auto-registers a debug controller). If we ever add server-rendered pages, an explicit rule for that prefix gets added — the current rule will tell us we forgot.
- **`HttpStatusEntryPoint(401)` instead of letting Spring pick a default**: with form login disabled and HTTP Basic disabled, Spring's default `AuthenticationEntryPoint` selection logic is unpredictable — versions of Spring Security have shipped with `Http403ForbiddenEntryPoint` as a fallback, or with one that emits a 401 + `WWW-Authenticate: Basic` header even when Basic is disabled. The explicit entry point pins the behavior: 401 with no `WWW-Authenticate` header, which matches what the SPA expects (no browser-driven Basic auth dialog).
- **Session creation policy `IF_REQUIRED`**: the default. Explicitly set so the intent is on the page. `STATELESS` would defeat session-cookie auth; `ALWAYS` would create a session for every health probe and waste DB rows in `SPRING_SESSION`; `IF_REQUIRED` creates a session only when a filter or a controller actually puts an attribute (the login handler in TASK-027 will trigger that on successful credential validation).
- **Form login / HTTP Basic / `/logout` all disabled**: keeps the active filter list to the minimum needed for cookie session auth. The login flow (TASK-027) will be a custom `@PostMapping("/api/auth/login")` controller that validates credentials and calls `SecurityContextHolder.getContext().setAuthentication(...)` + (via Spring Session) persists. Logout (TASK-029) is a custom `@PostMapping("/api/logout")` that calls `request.getSession().invalidate()`. Disabling Spring's auto-registered `/logout` filter avoids a path collision and keeps every public route under explicit control.
- **`SecurityConfig` lives in `com.trackify.config`, not `com.trackify.auth.config` or `com.trackify.common.security`**: the filter chain is a cross-cutting infrastructure concern that wires beans across the app (CORS source from `web`, future authentication providers from `auth`). It belongs with the other cross-cutting `@Configuration` classes (`WebConfig`, `JacksonConfig`, `OpenApiConfig`). The `auth` module owns authentication *logic* (UserDetailsService, login/logout controllers, password encoding) — TASK-025/026/027 land there. `common.security` is for shared helpers (current-user resolver, role-check predicates). Keeping the layers separate avoids a future merge where moving the filter chain into `auth` would force `auth` to depend on `WebConfig`'s CORS bean across module boundaries.

Follow-up risk / notes:
- **TASK-025 (auth properties binding)**: the dangling `trackify.auth.password.{encoder-strength,min-length}` and `trackify.auth.bootstrap.admin.*` properties in `application.yml` still have no `@ConfigurationProperties` class. TASK-025 owns that. The filter chain itself does not need them — the `PasswordEncoder` bean (BCrypt with the configured strength) is consumed by the login controller and registration service, not by `SecurityFilterChain` directly.
- **TASK-026 (registration) and TASK-027 (login)**: these will introduce a `UserDetailsService` (or an equivalent custom auth provider) that loads `User` rows by login and verifies the bcrypt hash. `SecurityConfig` does not need a `DaoAuthenticationProvider` bean today — Spring Security 6 auto-discovers a `UserDetailsService` bean and wires `DaoAuthenticationProvider` automatically when the `AuthenticationManager` is requested. If the login controller uses `AuthenticationManager.authenticate(...)` (the typical pattern), the chain is complete with no extra config in `SecurityConfig`. If a custom flow bypasses `AuthenticationManager` (e.g., manual `passwordEncoder.matches(...)`), the `UserDetailsService` bean is just unused — no harm.
- **TASK-028 (`/api/me` controller)**: the placeholder probe in `SecurityFilterChainTest` is `/api/me`. TASK-028 will wire a real controller that returns the current user. The 401 assertion in the test will continue to hold for unauthenticated requests after TASK-028 lands — the `authenticated()` rule fires before dispatcher routing. The test will need a parallel `@WithMockUser` test (or session-cookie-based test) added in TASK-028 to prove the 200-with-payload case; that is TASK-028's scope.
- **`/api/auth/login` security blast radius**: permitting all `/api/auth/**` includes future endpoints. Each one must be safe to expose anonymously (login, register, request-password-reset, complete-password-reset). `/api/auth/logout` is *not* anonymous and is intentionally outside this prefix — keeping logout on `/api/logout` (per architecture.md §11) prevents accidental anonymous logout-amplification. If a future task adds an authenticated `/api/auth/...` endpoint, it must add an explicit `requestMatchers(...).authenticated()` rule before the `/api/auth/**` line, or the task moves the new endpoint to a different prefix. Easy to overlook; flagging here.
- **`secure: true` cookie + local dev still unverified**: the prior progress note flagged that `SERVER_SERVLET_SESSION_COOKIE_SECURE` defaults to `true` and HTTPS is required for the browser to attach the cookie. TASK-024 does not fix that — it only configures the filter chain. Local dev login testing in TASK-027/031 will require either an HTTPS dev proxy or `SERVER_SERVLET_SESSION_COOKIE_SECURE=false` in `.env` for the local profile. This is a real foot-gun for the next iteration.
- **No `PasswordEncoder` bean here**: deliberately. Putting a `BCryptPasswordEncoder` bean in `SecurityConfig` would couple the security filter chain to the credential-hashing strategy. The encoder bean belongs in the auth module (TASK-025 or TASK-026) where the registration service lives. Adding it now would be scope creep; not adding it does not break anything because `AuthenticationManager` is not requested by anything yet.
- **Test depends on `WebConfig` being importable**: `SecurityFilterChainTest` imports `WebConfig` to satisfy the `CorsConfigurationSource` dependency. If `WebConfig` is ever renamed, split, or moved, the test import breaks immediately. The `@TestPropertySource` block duplicates the four CORS keys from `application.yml` because `@WebMvcTest` does not load `application.yml` automatically. If `WebConfig` grows new `@Value` keys in a future task, this test will fail to wire `WebConfig` and the breakage will surface fast — annoying but visible, which is the intended trade-off of keeping config in `WebConfig` instead of duplicating the CORS bean across tests.

Design choices and trade-offs:
- **Record over POJO**: Spring Boot 3 binds records to `@ConfigurationProperties` natively. Removes boilerplate, forces immutability. Loss vs class: no field-level Bean Validation annotations on synthetic accessors. For an MVP with simple ints + strings driven by env vars, validation can land in consumers (TASK-026 registration can check `password.length() >= props.password().minLength()` directly). Adding `@Validated` + parameter-level constraints is a backwards-compatible upgrade later.
- **Nested `Bootstrap` -> `Admin`** matches existing YAML shape (`trackify.auth.bootstrap.admin.login`) and leaves room for future bootstrap profiles. Flattening would force a YAML rewrite later.
- **Empty-string vs null for unset bootstrap admin values**: `application.yml` defaults each to `""` (`${AUTH_BOOTSTRAP_ADMIN_LOGIN:}`), so the record receives empty strings rather than null in normal operation. The seed runner can treat blank as "no admin configured" with a single `if (admin.login().isBlank()) return;`. Not switching to `Optional<String>` because YAML doesn't bind empty strings to `Optional.empty()` and the consumer normalizes anyway.
- **`AuthSecurityBeans` lives in `com.trackify.auth.application`, not `com.trackify.config`**: architecture.md §7.2 puts password hashing in the `auth` domain. Putting `PasswordEncoder` in `com.trackify.config` would couple the cross-cutting filter chain to credential strategy — exactly what the TASK-024 progress note argued against. Keeping it in `auth.application` lets future TASK-026/027 services depend on a domain-local `PasswordEncoder`.
- **`@EnableConfigurationProperties` on `AuthSecurityBeans`, not on `TrackifyApplication`**: scoping activation to the consumer keeps the auth module self-contained and grep-able. Avoids scattering activations across the root class.
- **Bean is `PasswordEncoder` (interface), implementation is `BCryptPasswordEncoder`**: consumers depend on the interface; swapping to `Argon2PasswordEncoder` later is a one-line change. `DelegatingPasswordEncoder` is overkill for a single-algorithm MVP — easy to add later if migration support is needed.
- **Test uses `ApplicationContextRunner`, not `@SpringBootTest`**: full app context activates JPA, Flyway, Postgres — none of which are relevant to property binding. `ApplicationContextRunner` boots a tiny isolated context (~100 ms), runs assertions, cleans up. Canonical Spring Boot pattern for testing config-properties binding. Means `./mvnw test` runs full-green even when Postgres is not running.

Harmless (the auto-generated default user has no path through the SecurityFilterChain because form login is disabled) but noisy. TASK-026 will introduce a custom `UserDetailsService` that loads from `UserRepository`, causing the auto-config to back off on its `@ConditionalOnMissingBean` guard.

The login controller can then delegate to `AuthenticationManager.authenticate(...)`. Either pattern works; the bean is pre-positioned for both.

TASK-026 — Implement local user registration service
Date: 2026-04-26
================================================================================

What changed:
- `backend/src/main/java/com/trackify/auth/application/RegisterUserCommand.java`: new value-object record carrying the four registration inputs (`login`, `email`, `displayName`, `rawPassword`). Lives in `auth.application` because it is the input contract for an application service, not a domain entity. Raw password lives only on the call stack — never reaches persistence.
- `backend/src/main/java/com/trackify/auth/domain/DuplicateLoginException.java`: new typed `RuntimeException` thrown when the caller asks to create a user whose login already exists. Lives in `auth.domain` because duplicate-login is a business-rule failure (domain rule: logins are unique), not an infrastructure concern. Surfacing a typed exception lets future TASK-027 / controller layers map it to a 409 cleanly instead of catching `DataIntegrityViolationException` and string-matching the constraint name.
- `backend/src/main/java/com/trackify/auth/application/UserRegistrationService.java`: new `@Service` with one method, `register(RegisterUserCommand)`, marked `@Transactional`. Order of operations: (1) password length check against `AuthProperties.password().minLength()`, (2) `userRepository.existsByLogin(...)` pre-check throwing `DuplicateLoginException`, (3) `passwordEncoder.encode(...)`, (4) `userRepository.save(new User(...))` with the hash. Returns the persisted `User` for downstream callers (TASK-027 login auto-flow, future seed runner). Constructor-injects `UserRepository`, `PasswordEncoder`, `AuthProperties` — all three already exist (TASK-022, TASK-025).
- `backend/src/test/java/com/trackify/auth/application/UserRegistrationServiceTest.java`: new pure JUnit + Mockito unit test, no Spring context. Three cases: (a) happy path verifies the service hashes the password (asserts persisted hash equals the encoder's stub output AND is not equal to the raw password — the property the test step calls out), captures the `User` via `ArgumentCaptor` and checks every field, and confirms the encoder ran exactly once; (b) duplicate-login case verifies `DuplicateLoginException` fires and that neither `passwordEncoder.encode(...)` nor `userRepository.save(...)` is called — the short-circuit ordering matters so we never burn a bcrypt round on a doomed request; (c) under-min-length case verifies the password rule fires before the existence check, so we never even hit the database for an obviously-bad request.

What was tested:
- `./mvnw -q compile`: clean (exit 0). New types compile against existing pom.
- `./mvnw test`: BUILD SUCCESS. Tests run: 10 (up from 7), Failures: 0, Errors: 0, Skipped: 0. New: `UserRegistrationServiceTest` x3 (`registerHashesPasswordAndPersistsUser`, `registerRejectsDuplicateLoginBeforeHashingOrSaving`, `registerRejectsPasswordShorterThanConfiguredMinLength`). Existing 7 tests unchanged. The `[ERROR]` stack visible mid-output is from `GlobalExceptionHandlerTest`'s expected `log.error` call when it asserts the 500-path — same as in TASK-024 / TASK-025 runs, not a regression.
- The user prompt asked for `./gradlew -p backend ...`. Project is Maven (`./mvnw`) per CLAUDE.md; ran the equivalent Maven steps. Same as prior tasks.

Design choices and trade-offs:
- **Pre-check `existsByLogin` instead of relying on the DB unique constraint**: a pre-check costs one extra SELECT but lets the service throw a typed `DuplicateLoginException` deterministically, instead of catching `DataIntegrityViolationException` and inspecting the constraint name (which is fragile across Postgres versions and across H2 if anyone ever spins up an in-memory test profile). Race condition still exists between the SELECT and the INSERT, but the DB unique index is the actual guard — at worst the loser of a race gets a 500 from the unhandled `DataIntegrityViolationException`, which is acceptable for an MVP. A future TASK-077 hardening pass can add a `@ExceptionHandler(DataIntegrityViolationException.class)` mapping if this ever happens in practice.
- **No email pre-check**: TASK-026's test step explicitly says "rejects a duplicate login" — singular, login-only. The `users` table has `UNIQUE` on email too (V2 migration), so a duplicate email ultimately fails at insert time. Adding a pre-check + `DuplicateEmailException` now would be scope creep with no covering test step. If email-collision UX matters later, it's a one-line addition. Keeping the surface area small now keeps the diff reviewable and the test boundary tight.
- **`IllegalArgumentException` for password-too-short, not a typed `WeakPasswordException`**: the password rule is one numeric threshold, the message embeds the configured min length, and consumers (controller layer, TASK-027) can catch `IllegalArgumentException` and translate it. Inventing a type hierarchy for a single rule is premature. Once registration grows multiple validations (banned passwords, special-char policy, etc.) or once a controller needs different status codes per rule, splitting into typed exceptions becomes worth it.
- **Validation in the service, not via Bean Validation on `RegisterUserCommand`**: Bean Validation would pull in `@NotBlank`, `@Email`, `@Size` — *but* the size constraint is dynamic (driven by `AuthProperties.password().minLength()`), which Bean Validation cannot do without a custom `ConstraintValidator`. Keeping the rule in the service keeps the dynamic-config link explicit and lets the test exercise the real coupling. Static rules (`@NotBlank` login/email, `@Email` email format) belong on a future request DTO at the controller boundary (TASK-027 territory), not on this internal command.
- **`@Transactional` on the service method**: only one repository write today, so the boundary is trivial. Marked anyway because TASK-027 will likely auto-login the new user (loading + setting authentication context within the same transaction) and TASK-034 will piggyback workspace creation on registration. Setting the boundary now means future additions don't introduce subtle "did this commit yet" bugs.
- **Returning `User` vs returning the new id (UUID) vs returning a DTO**: returning the entity is the path of least resistance for TASK-027 (it can immediately call `SecurityContextHolder.getContext().setAuthentication(...)` with the loaded principal) and for TASK-034 (workspace creation needs the user id). Risk: the entity escapes the application layer. Mitigation: only `auth.application` and the future `auth/controller` consume it, and the controller will map to a DTO before serialization (architecture.md §7.1). If/when this contract leaks across modules, a return-type refactor is mechanical.
- **Not adding a `UserDetailsService` here**: that is TASK-027's territory (login + Spring Security wiring). Adding it now would mean adding a bean that nothing consumes, which would silence the auto-config "Using generated security password" warning prematurely and tangle TASK-026/027 boundaries.
- **Test uses `ArgumentCaptor` instead of stubbing `save` to return a fixed value**: lets the test verify the *exact* `User` instance the service constructed (including that the password field is the hash, not the raw input) instead of trusting whatever `save` returns. Catches a class of bugs where the service might accidentally pass `command.rawPassword()` to the `User` constructor.
- **Test does not boot Spring**: pure Mockito + JUnit 5. ~50 ms per test vs. ~1 s for `@SpringBootTest`. Three tests, all sub-200 ms total, no Postgres needed — `./mvnw test` stays runnable on a clean clone.

Follow-up risk / notes:
- **TASK-027 (login endpoint)**: now has all the building blocks. Two viable patterns: (a) build a custom `UserDetailsService` that loads `User` by login, then plug it into Spring Security's `DaoAuthenticationProvider` (auto-configured because both `UserDetailsService` and `PasswordEncoder` beans exist), and use `AuthenticationManager.authenticate(...)` from a `@PostMapping("/api/auth/login")`. (b) hand-roll the credential check by calling `userRepository.findByLogin(...)` and `passwordEncoder.matches(raw, user.passwordHash())`. (a) is more idiomatic Spring Security and lights up the rest of the framework's auth infrastructure (e.g., method security `@PreAuthorize`); (b) is simpler but bypasses framework checks. Recommend (a). Either way, after credential validation the controller calls `SecurityContextHolder.getContext().setAuthentication(...)` and Spring Session JDBC persists the session.
- **TASK-027 controller will need `POST /api/auth/register`**: per architecture.md §11. The controller will accept a request DTO (with Bean Validation), translate to `RegisterUserCommand`, call `userRegistrationService.register(...)`, and return a session (auto-login is the natural UX). This task did not add the controller because TASK-026 is scoped to "service" only — adding a controller now would tangle the `tasks.json` boundary.
- **TASK-034 (auto-create personal workspace on first login)**: the cleanest place to hook this is *after* a successful login (reuses the path for both registered and pre-existing users) — not inside `UserRegistrationService.register(...)`. Putting it in registration would miss the case where TASK-027 needs to create a workspace for the bootstrap admin (which is seeded directly via the registration service from a runner, not via login). TASK-027 / TASK-034 will resolve this by checking-and-creating in the login success handler. Flag: do not add `WorkspaceService.createPersonal(...)` to `UserRegistrationService` even when it's tempting; keep registration single-purpose.
- **No `AUTH_BOOTSTRAP_ADMIN_*` seed runner yet**: the env-var-driven seed admin still has no `ApplicationRunner` consumer. With `UserRegistrationService` now in place, that runner is a ~15-line class that reads `AuthProperties.bootstrap().admin()`, returns early on blank login, and calls `register(...)`. Likely lands in TASK-027 or alongside the first manual smoke-test setup. Flag: any seed runner must run *after* Flyway has executed (default behavior of `@Component` with `ApplicationRunner` already satisfies this) and must tolerate a re-run (the duplicate-login pre-check makes it idempotent for free — second boot throws `DuplicateLoginException`, which the runner can swallow with a log line).
- **Concurrent-registration race**: two simultaneous calls with the same login both pass `existsByLogin` (returns false), both proceed to `save`, second one fails on the unique constraint with `DataIntegrityViolationException`. Today that surfaces as a 500 via `GlobalExceptionHandler.handleGeneric`. Acceptable for MVP. Hardening (TASK-077): add `@ExceptionHandler(DataIntegrityViolationException.class)` that returns 409. Not in scope here.
- **Password length check ignores leading/trailing whitespace**: `"        "` (8 spaces) passes the length-8 check. For an MVP, fine — bcrypt hashes whatever it gets. A future password-policy task can enforce non-whitespace + complexity rules. Flagging because it surprised me when reviewing the test — the rule is purely length, intentionally.
- **`User` entity has setters**: `User.setPasswordHash`, `setLogin`, etc. exist (carried over from TASK-022). Registration service uses the constructor only and never touches setters, so it is not exercising the mutability today. Setters might be removed in a later refactor when the entity is closed off — does not affect TASK-026.
- **No frontend changes**: the registration UI is not yet defined as a task. TASK-031 is sign-in only. A future task will add a registration form if/when self-signup is enabled.
- **No DB / migration changes**: pure service code. V1 (users) and V2 (session) unchanged.
- **Reviewer note for TASK-027**: when the login controller calls `AuthenticationManager.authenticate(...)`, it expects `BadCredentialsException` for a wrong password and `UsernameNotFoundException` for a missing user. Spring's default behavior collapses the second into the first (to avoid login-existence enumeration via timing). Design choices and trade-offs:
- **`AuthenticationManager` from `AuthenticationConfiguration` instead of building a `DaoAuthenticationProvider` by hand**: with both `UserDetailsService` (LocalUserDetailsService) and `PasswordEncoder` beans on the context, Spring Security 6 auto-wires a `DaoAuthenticationProvider` and the global `AuthenticationManager` already knows about it. Pulling the manager out via `AuthenticationConfiguration` is the canonical pattern and avoids duplicating provider config in two places. Building a `DaoAuthenticationProvider` by hand would force me to also declare a separate `AuthenticationManager` and carefully avoid the global one — easy to introduce a "two managers, one wins" bug.
- **Custom `LocalUserPrincipal` instead of Spring's built-in `org.springframework.security.core.userdetails.User`**: the built-in carries only `username` + `password` + authorities. Every authorization check against a workspace/project membership ultimately needs the `users.id` UUID. Either I carry it on the principal (this approach) or I re-query `UserRepository.findByLogin(...)` on every request that needs a user id. The principal lives in memory inside the `SecurityContext` for the life of the session, so adding a UUID field has near-zero cost; re-querying the DB on every authenticated request to translate login → uuid would be wasteful. Carrying it from the start avoids a future churn task that would touch every authorization check.
- **`SecurityContextRepository` as an explicit `@Bean`, wired into both the filter chain and the controller**: in Spring Security 6 the default behaviour split into "read on entry" (handled by `SecurityContextHolderFilter`, which receives the repo from `securityContext(...)` config) and "write on exit" (the application now must call `saveContext` itself). If the controller built a `HttpSessionSecurityContextRepository` inline and the filter chain used a *different* default, reads and writes could land in different stores. Sharing one bean across both wiring points keeps them aligned. Default `HttpSessionSecurityContextRepository` is fine because Spring Session JDBC swaps the underlying `HttpSession` for a JDBC-backed one transparently — the repository never sees the difference.
- **Login response is `{userId, login}`, not `{}` and not the full user**: returning `{}` would be cleaner ("the cookie carries the truth, fetch /api/me") but forces the SPA to make a second round-trip before it can render. Returning the full user record from the login endpoint would couple this contract to the `/api/me` payload shape and make a future change to one rebuild the other. The compromise: the bare identity needed to confirm "yes you are signed in as X" lets the SPA show optimistic UI immediately while `/api/me` (TASK-028) hydrates the full profile.
- **`@ExceptionHandler(AuthenticationException.class)` on the controller, not on `GlobalExceptionHandler`**: TASK-024's progress note (and the `GlobalExceptionHandler` Javadoc) explicitly defer 401/403 mappings to TASK-077 ("Standardize 401, 403, and 404 API responses"). Adding a global mapping now would land in TASK-077's territory and force a re-decision later. The controller-local handler is scope-tight: it covers `LoginController`'s methods only, returns the `ApiError` envelope today, and TASK-077 can lift it to global without rewriting the body shape (or replace it entirely if the global rule diverges).
- **Catching the *broad* `AuthenticationException`, not just `BadCredentialsException`**: `DaoAuthenticationProvider` collapses `UsernameNotFoundException` into `BadCredentialsException` *only when* `setHideUserNotFoundExceptions(true)` is set (the default). If a future config change flips that — or if some other authenticator path throws `DisabledException`, `LockedException`, etc. — we still want a single-status 401 envelope rather than a 500 from `GlobalExceptionHandler.handleGeneric`.
- **`AuthenticationException` subclasses *do not* include `AccessDeniedException`**: that one is for *authorized* users hitting forbidden resources (a 403 case) — it extends `RuntimeException` directly, not `AuthenticationException`. So this handler will not accidentally swallow the future TASK-076 forbidden-membership case.
- **`@WebMvcTest` slice instead of `@SpringBootTest`**: `@SpringBootTest` would try to start JPA + Flyway + the real Postgres — none of which are needed to test the controller's auth orchestration. The slice mocks `UserRepository`, runs the real `AuthenticationManager` + `PasswordEncoder` + `LocalUserDetailsService`, and produces the same authentication path as production for the bits that matter. Test runs in <500ms with no DB dependency.
- **`@MockitoBean` instead of `@MockBean`**: `@MockBean` is deprecated in Spring Boot 3.4 in favor of `@MockitoBean` (package `org.springframework.test.context.bean.override.mockito`). Using the new annotation now keeps the test compatible across the upgrade path; the behaviour is identical for our case.
- **`ReflectionTestUtils.setField(user, "id", uuid)` to set the UUID in tests**: `User`'s id is generated by JPA on insert (`@GeneratedValue(strategy = UUID)`) and there is no public setter. Using `ReflectionTestUtils` is the canonical Spring way to materialize a "persisted-looking" entity in a unit/slice test without booting JPA. The alternative (adding a package-private setter or a test-only constructor) would weaken the entity's invariants for the sake of a test.
- **Test password uses encoder strength 4 (vs. production default 10)**: configured via `@TestPropertySource`. BCrypt cost is 2^strength, so 4 is ~64x faster than 10. Doesn't change behavior; just keeps the slice test fast. Production-strength is exercised by `AuthSecurityBeansTest` already.
- **`JacksonConfig` added to imports**: the existing `@WebMvcTest` slice tests in this project don't all import it because they don't serialize record-shaped responses. `LoginResponse` is a record, and Jackson's record support has surprised people in the past. Importing the project's actual `JacksonConfig` makes the slice match production wiring. Defensive but cheap.

Design choices and trade-offs:
- **Controller location (`user.controller`, not `auth.controller`)**: architecture.md §11 groups `/api/me` with the auth/session section, which might suggest `auth.controller`. However, the data the endpoint returns is a `user`-domain projection (`User` entity → `MeResponse`), and the service that fetches it lives in `user.application`. The auth-grouping in architecture.md is an API-path concern, not a code-ownership concern. This interpretation is noted explicitly in the controller Javadoc.
- **Option 2 for principal design (keep principal lean, load full user from DB per request)**: `LocalUserPrincipal` carries only `userId` + `username` (login), not `email` or `displayName`. `/api/me` therefore does one `findById` per call. For a once-per-page-load identity probe the extra DB round-trip is negligible; correctness wins over saving one SELECT. This is the same trade-off documented in the task brief.

- **`NotFoundException` for missing user id**: if the user row were deleted while a session is still alive, `findById` returns `Optional.empty()` and `MeService` throws `NotFoundException`. `GlobalExceptionHandler` maps this to 404. The alternative is silently returning `null` or 401 — both are wrong (a deleted user with a dangling session is an integrity problem, not an "unauthenticated" state). This is defensive programming that costs nothing at runtime under normal conditions.
- **`@AuthenticationPrincipal` annotation on the controller parameter**: Spring MVC resolves the typed principal directly from the `SecurityContext` via `AuthenticationPrincipalArgumentResolver`. Alternatively, we could assert `principal != null` at the top of the method — a future task (TASK-077 or the OAuth2 integration task) should add that guard once the second principal type exists.
- **Test uses `authentication()` post-processor, not `@WithMockUser`**: `@WithMockUser` installs a `UsernamePasswordAuthenticationToken` whose principal is a plain Spring `User` object, not a `LocalUserPrincipal`. The controller would throw a `ClassCastException` on `(LocalUserPrincipal) authentication.getPrincipal()`. The `authentication()` post-processor from `spring-security-test` lets us install the exact token and principal type the real flow would produce. This is the cleanest pattern for slice tests with a typed principal.
- **`@MockitoBean` instead of `@MockBean`**: Spring Boot 3.4 replacement, consistent with `LoginControllerTest`. Same behavior, forward-compatible.

Design choices and trade-offs:
- **`/api/me` 401 → `null` data, not thrown error**: there are two reasonable shapes for "is the user signed in?" with TanStack Query. - **`staleTime: Infinity` + `retry: false` + `refetchOnWindowFocus: false`** on the me query: the session cookie's lifetime is controlled by the backend; refetching on every window focus would hammer `/api/me` for no benefit because the cookie has not changed since mount. The provider is app-shell infrastructure (how the app boots its session), but the consumer hook is a domain-feature concern (how a feature reads "current user"). Keeps the import direction one-way: features import from `app/providers/AuthContext`, never the other way around.
- **`queryClient.clear()` on signOut + explicit re-seed of `auth.me`**: when the user logs out, every cached query is potentially user-scoped (workspaces, projects, tasks). Selectively invalidating each key as those features land would force re-touching this file later. `clear()` drops everything once and is the safest signal; it also drops the now-stale `auth.me` entry, so I re-seed it as `null` immediately afterward so the provider's `useQuery` reads `null` synchronously instead of going back to the loading state.
- **`signIn` returns the full `AuthUser` or throws**: the SPA's sign-in flow (TASK-031) needs to know whether sign-in succeeded so it can navigate. Returning the user lets the page do `await signIn(...)` then redirect — no second `useAuth()` read needed. The thrown `ApiError` propagates the backend's 401 envelope (`INVALID_CREDENTIALS`) so the form can render the error message.
- **`refresh()` exposed as part of the context**: TASK-034 (auto-create personal workspace on first login) and any future auth-event listener may need to re-pull `/api/me` mid-session. Having `refresh` on the context surface keeps that one-line for callers and avoids `queryClient.invalidateQueries(...)` sprinkled everywhere with the literal key.

Design choices and trade-offs:
- **Two named guards instead of one with a `mode` prop.** A single `<AuthGate mode="require-auth" />` component would centralize the `useAuth` call but would also require every consumer to remember the mode prop and the type-narrow it implies. Two named components read better in `routes.tsx` (`<RequireAuth>` is self-documenting at the call site) and lets each guard ignore the dimension the other cares about. The cost is one extra component definition; the benefit is no boolean prop and no conditional return chains inside one body.
- **Single file `RouteGuards.tsx` instead of one file per guard.** The provider pattern in this codebase (`AuthProvider.tsx`, `QueryProvider.tsx`, `ThemeProvider.tsx`) is one-component-per-file. - **Wrap layouts, not pages.** Two practical placements: (a) wrap each *page* component in a guard, or (b) wrap the *layout route* element in a guard. (b) is one wrapper per layout vs. one per page; it cannot drift when new pages are added; and `AuthLayoutRoute` / `AppShellRoute` are already the natural boundary between "anonymous-allowed" and "auth-required" UI. Putting the guard on the layout means every protected page automatically inherits gating without remembering to import the guard at each page. The cost is that both layouts now include a `useAuth` call — fine, since the context lookup is O(1) and the layouts already render unconditionally on every authenticated render.
- **`replace` on both `<Navigate>` calls.** A `push` would put the protected URL into the history and a back-button would loop the user through the redirect again. `replace` is the standard React Router pattern for redirects-as-policy. SignInPage already uses `navigate('/', { replace: true })` on success (TASK-031), so the back button cannot revisit `/sign-in` after a successful login either — the history stays clean from both directions.
- **Loading shell, not redirect-during-loading.** While the initial `/api/me` round-trip is in flight, `useAuth().status === 'loading'`. If `RequireAuth` redirected on `'loading'`, a freshly-loaded authenticated user would briefly see `/sign-in` while their session restored — a flicker that's both ugly and slightly misleading (the user is *not* signed out, just waiting for the bootstrap probe). The neutral loading shell is the correct intermediate state. Inverse argument applies to `RequireAnonymous`: redirecting while loading would briefly send an unauthenticated user from `/sign-in` to `/`, which would then bounce them back to `/sign-in`. Two redirects per pageload to land on the same place is a pure UX regression. The loading shell short-circuits both flicker patterns.

If we ever decide we don't want post-login bounce-back, we can remove the prop without affecting protection. Including it costs three tokens and zero behaviour.
- **No "remember intended URL across signOut" handling.** `RequireAuth` only forwards `from` on the *first* unauthenticated visit. If the user logs out and lands on `/sign-in`, there's no "from" — they get the dashboard on next login. This is fine and is the typical signed-out experience; there's no acceptance criterion calling for anything else.
- **No use of `<Navigate>` element on the route definition.** React Router's data-router lets you embed `<Navigate>` as the route element, e.g. `{ path: '/sign-in', element: status === 'authed' ? <Navigate to="/" /> : <SignInPage /> }`. That requires reading auth state at the router-creation site, which would tie the `router` const to a hook context that doesn't exist outside React render. Wrapping inside the route element via guard components is the canonical React Router 7 pattern for auth-conditional routing.

Design choices and trade-offs:
- **Opaque UUID FKs instead of `@ManyToOne` associations.** The textbook JPA approach would be `@ManyToOne private User owner;` and `@ManyToOne private Workspace workspace;` on the member row. I chose plain `UUID ownerId`/`workspaceId`/`userId` deliberately for two reasons. (1) Architecture.md section 7 calls for a modular monolith with crisp module boundaries; if `Workspace` references `User` directly, the `workspace` package now compiles only when `user.domain.User` is on the classpath, which leaks the user module's internal entity into a peer module. (2) It keeps the JPA graph shallow: no eager-load decisions to make, no LazyInitializationException risk, no fetch-join surprises in later board/timeline read paths. The cost is that joining workspace plus owner-display-name requires an explicit JPQL or projection, but every downstream task that needs that join (TASK-035, TASK-042) will assemble its own DTO anyway.
- **`OWNER`/`ADMIN`/`MEMBER`/`VIEWER` role taxonomy.** Architecture.md section 9 mentions "role-based actions like project admin, editor, viewer" in the *project* context, not the workspace context. For workspaces the doc only says "membership and roles". I picked a four-rank taxonomy to leave room for the natural distinctions: `OWNER` is the workspace creator (matched 1:1 with `workspaces.owner_id`), `ADMIN` can manage projects and members, `MEMBER` is the default seat, `VIEWER` is read-only. The CHECK constraint can be loosened in a later migration if more roles are needed; can't easily be tightened later, so erring narrow. TASK-034 will create the personal workspace with `OWNER` for its single member.
- **`ON DELETE RESTRICT` on `workspaces.owner_id`, `ON DELETE CASCADE` on `workspace_members`.** The asymmetry is intentional. A workspace member row going away when its user is deleted is correct (the membership is meaningless without the user). A whole workspace going away when its owner is deleted is *not* correct: that workspace probably has projects and tasks belonging to other members. RESTRICT forces the application layer to handle owner deletion explicitly (transfer ownership or delete workspace first). User deletion isn't in MVP scope anyway, but the schema baseline is the right place to encode "destructive cascade only where it is unambiguously safe."
- **Slug column on `workspaces` even though no API exposes it yet.** Slug is the URL-safe handle (`/workspaces/personal-mikhail/...` style). The architecture doesn't mandate slugs in section 10, but the dashboard URL flow in section 8 implicitly assumes some human-readable workspace identifier exists. Adding the column plus unique index now is cheap; backfilling an `ALTER TABLE` migration later for every existing workspace would be more work and would force a dual-read/dual-write window. TASK-034 will populate it with a derived slug (e.g., from the user's login).
- **No `WorkspaceMember` `@PreUpdate`.** Membership rows are append-only at this stage; role changes will be handled later (or by deleting plus reinserting). Skipping the `@PreUpdate` makes the no-`updated_at` schema column intentional rather than accidental.
- **Repositories expose only what TASK-034/035/076 need.** I resisted adding `findAllByWorkspaceId`, `countByWorkspaceId`, `findByOwnerId`, etc. The task scope is "support workspaces and workspace_members"; adding speculative finders now would be premature abstraction (CLAUDE.md cross-cutting rules: "no premature abstractions"). When TASK-034 lands and needs `findByOwnerIdAndUserId` or whatever, it can add the method then with a real call site.
- **Index only on `workspace_members.user_id`, not on `workspace_id`.** Postgres's unique constraint on `(workspace_id, user_id)` already creates a btree index that is leftmost-prefixed by `workspace_id`, so any `WHERE workspace_id = ?` query (e.g., "list members of this workspace") can use it. A separate `workspace_id` index would be redundant. The standalone `user_id` index is needed because user_id is the *second* column of the unique index and therefore not indexed-leftmost on its own.
- **No tests added.** The task's `test_steps` is `./mvnw compile`. The codebase pattern has been to add tests where the task asks for them (TASK-026, TASK-027, TASK-028 all explicitly request unit/MockMvc tests; TASK-022, entity plus repository, doesn't and didn't get a test). Following the established pattern: TASK-033 doesn't ask for a test; the next workspace task that adds *behavior* (TASK-034) will exercise both repositories through its application service.

Design choices and trade-offs:
- **Hook in `LoginController`, not via `ApplicationListener<InteractiveAuthenticationSuccessEvent>` or a custom `AuthenticationSuccessHandler`.** Three reasons. (1) The login flow in this project is *manual* — `LoginController` already explicitly calls `authenticationManager.authenticate` and `securityContextRepository.saveContext`, so post-auth side effects naturally compose at the controller level rather than at a Spring Security extension point. (2) An event listener would decouple the bootstrap call from the request transaction in a way that buys nothing — there's no async dispatch, no other listeners, no observability layer hanging off auth events. (3) Test ergonomics: a controller-level call is trivially mockable in `LoginControllerTest` (a single `@MockitoBean` line); an `ApplicationListener` would force every login test to either spin up the listener bean or globally suppress it. The `LoginController` site is the canonical "after authenticate, before respond" hook in this codebase and that's where this belongs.
- **Idempotency by membership state, not by a `users.bootstrap_done` flag.** A flag column would require a fifth Flyway migration and would couple "has a personal workspace" to a denormalized boolean that could drift from reality (admin deletes a workspace -> flag still says "done" -> user logs in again with no workspace). Querying `workspace_members.user_id` is one indexed lookup (the `workspace_members_user_id_idx` index from V4) and answers the actual question — "does this user already participate in any workspace?" — directly. Future workspace-management UI (delete workspace, leave workspace) automatically composes correctly: if the user ends up with zero memberships, their next login re-bootstraps. That matches the user-visible promise of the system better than a sticky flag.
- **Idempotency on *any* membership, not specifically a "personal" one.** A more conservative implementation would check "does the user own a workspace whose slug equals their login?" — only skipping bootstrap when the *personal* workspace exists. I rejected that: once email invites land (out of MVP scope) a user might receive a workspace invitation before ever creating one of their own, and we don't want to force-create a "personal" workspace on top of an already-functional invited one just because the slug doesn't match. The acceptance criterion is "guarantees exactly one personal workspace and one owner membership" *for the first-login case* — and the start condition is "a signed-in user may exist without any workspace." Both are satisfied by membership-presence idempotency.
- **Slug derivation: `toKebabCase(login)` -> on collision, append a 4-char hex fragment from `UUID.randomUUID()`.** Two pragmatic choices baked in. (1) One retry, not N retries: if the suffixed slug is *also* taken (1-in-65k odds for a single-user collision, much less for repeat collisions), the database unique constraint will surface a 5xx and the user can retry login. The expected MVP user count is small enough that bounded retry is overkill; the unique constraint is the safety net and Hibernate will throw a `DataIntegrityViolationException` mapped through `GlobalExceptionHandler` (TASK-011). (2) Hex fragment over numeric suffix (`-1`, `-2`, ...): a numeric suffix would require a `findByOwnerIdOrderBySlugDesc`-style query plus a counter, while hex is collision-resistant in one shot. The aesthetic cost (`alice-7f3a` vs `alice-1`) is acceptable for what is currently an internal slug.
- **Workspace name `"{login}'s workspace"` instead of `"Personal"`.** A literal "Personal" name would be ambiguous when a user later joins multiple workspaces (which "Personal"?). Including the login in the default name makes the workspace switcher (TASK-037) self-explanatory at a glance. The name is mutable later (workspaces will get rename UI in scope or post-MVP) so this is just a sensible default, not a hard contract.
- **No new migration.** The V4 schema from TASK-033 already has every column needed: `workspaces.slug` (unique), `workspaces.owner_id`, `workspace_members.role` (CHECK includes OWNER). Adding a `bootstrapped_at` column on `users` was tempting (audit purposes) but it's pure speculation right now and would force `User` entity changes for no observable benefit. CLAUDE.md cross-cutting rule: no premature abstractions, no speculative columns.
- **Mock-based unit test for the service, not `@DataJpaTest` against a real H2/Postgres.** The behavioural contract being verified is "given empty `findAllByUserId`, save exactly one Workspace and one WorkspaceMember" and "given non-empty, save nothing." That contract is fully expressed at the repository-call boundary; a `@DataJpaTest` would re-test that JpaRepository's `save()` actually inserts a row, which is a Spring/Hibernate concern, not a TASK-034 concern. The `LoginControllerTest` already sits behind `@WebMvcTest` with the full Spring Security filter chain wired up, and the existing `@SpringBootTest` end-to-end test surface implicitly exercises Flyway + JPA validate against a real Postgres on every test run, so the persistence layer is not under-tested.
- **`LoginControllerTest` updated minimally — `@MockitoBean` only.** The bootstrap call is invoked-and-discarded from the controller's POV (return type is `void`, no thrown checked exceptions), so the tests don't need to assert anything about it; verifying the existing assertions (200, session, principal identity, 401, no session) still hold under the new wiring is sufficient to prove the bootstrap call doesn't break the login contract.
- **Static `toKebabCase` package-private, not private.** It is small enough to be unit-testable independently and the test exercises it directly. Marking it package-private lets the test live in the same package without using reflection.

Follow-up risk / notes:
- **Slug collision retry is 1-deep.** If the `{login}-{4hex}` slug happens to *also* collide (vanishingly rare in practice), the underlying `UNIQUE` constraint on `workspaces.slug` will surface as a `DataIntegrityViolationException` and the login response will be a 500. Future hardening: bump the fragment length, add a bounded retry loop, or switch to a different uniqueness strategy. Not blocking for MVP — the current user volume makes this an academic risk.
- **No transaction-scope check beyond `@Transactional`.** The `ensurePersonalWorkspace` call runs inside the controller's request thread, after the security context has already been persisted to the session. If the bootstrap transaction throws (e.g., a transient DB failure), the user has *already* received an authenticated session cookie but no workspace was created. Their next login will re-attempt the bootstrap (idempotency carries us through), but the *current* request will return 500 instead of the login response. A more defensive implementation would wrap the bootstrap call in a try/catch and log + continue. I left it strict on purpose: surfacing the failure is a better-than-silently-broken default for the MVP, and idempotency means the worst case is "user sees one login fail, retries, gets in."
- **`LoginController` is not `@Transactional`.** The `@Transactional` is only on `WorkspaceBootstrapService.ensurePersonalWorkspace`. The `findAllByUserId` + `existsBySlug` + 2x `save` form the boundary; auth + session writes are outside that boundary. This matches the project pattern of "transactions live in `application/`, not `controller/`" (CLAUDE.md modular monolith section).
